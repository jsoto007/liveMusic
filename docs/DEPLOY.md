# Deploying to Render

The repo already contains [`render.yaml`](../render.yaml), a Blueprint that
creates everything at once: a Postgres database, a key-value store for the rate
limiter, the API, the static web bundle, and two cron jobs. You do not create
services by hand — you point Render at the repo and fill in the secrets.

Budget about 30 minutes, most of it waiting for the first build.

---

## Before you start

Have these three accounts open, because Render will ask for their keys and you
cannot finish without them:

| Service | What for | Free tier? |
|---|---|---|
| [Cloudflare R2](https://dash.cloudflare.com) | audio and images | 10 GB storage, no egress fee |
| [Resend](https://resend.com) | sending email | 3,000/month |
| [LocationIQ](https://locationiq.com) | address autocomplete | 5,000 lookups/day |

You can deploy without them — the app degrades honestly (uploads return 503,
mail is logged instead of sent, address fields become plain text) — but nothing
that needs them will work.

### Get the R2 credentials

1. Cloudflare dashboard → **R2** → **Create bucket**. Name it `live-msc-media`.
2. **R2** → **Manage API Tokens** → **Create API Token**. Permission:
   **Object Read & Write**, scoped to that bucket.
3. Copy the **Access Key ID**, the **Secret Access Key**, and your **Account
   ID** (it is in the URL, and on the R2 overview page).

Then — and this is the step people skip — set the bucket's CORS policy.
The server uses presigned **PUT** (not POST — R2 returns 501 on presigned POST),
so `PUT` must be in `AllowedMethods` and `Content-Type` must be in
`AllowedHeaders` (the signature pins it).

**Option A — apply with the CLI (recommended):**

```bash
cd apps/server && flask --app app media configure-cors
```

This reads `FRONTEND_URL` from your environment and applies the correct policy
automatically, including `HEAD` for completion checks.

**Option B — apply manually** in the Cloudflare dashboard
(**R2 → your bucket → Settings → CORS Policy**), replacing the origin with your
real web URL once you have it (step 3 below):

```json
[
  {
    "AllowedOrigins": ["https://live-msc-web.onrender.com"],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["Content-Type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

Add your custom domain to `AllowedOrigins` when you attach one. Without this
the browser blocks every upload before a byte leaves the page, and the failure
looks like a bug in the app rather than a bucket setting.

### Get the Resend key

1. Add and verify your sending domain (Resend walks you through the DNS
   records). This is not optional — mail from an unverified domain goes to
   spam.
2. **API Keys** → **Create**. Copy it.
3. Decide your From address, e.g. `notices@yourdomain.com`.

### Get the LocationIQ key

Sign up, then **Access Tokens** → copy the token. Use the `us1` endpoint unless
you are in the EU, in which case set `LOCATIONIQ_BASE_URL` to the `eu1` one.

## 1. Create the Blueprint

1. [dashboard.render.com](https://dashboard.render.com) → **New** →
   **Blueprint**.
2. Connect the GitHub repo (`jsoto007/liveMusic`) and pick the `main` branch.
3. Render reads `render.yaml` and shows you five resources:
   `live-msc-db`, `live-msc-api`, `live-msc-web`, `live-msc-cache`,
   `live-msc-reminders`, `live-msc-sweeper`.
4. It will prompt for every value marked `sync: false`. Fill them in:

| Key | Value |
|---|---|
| `R2_ACCOUNT_ID` | from Cloudflare |
| `R2_ENDPOINT_URL` | **leave empty** unless you have a custom endpoint |
| `R2_ACCESS_KEY_ID` | from the R2 API token |
| `R2_SECRET_ACCESS_KEY` | from the R2 API token |
| `R2_BUCKET` | `live-msc-media` |
| `R2_PUBLIC_BASE_URL` | **leave empty** — see the note below |
| `MAIL_FROM_ADDRESS` | `notices@yourdomain.com` |
| `RESEND_API_KEY` | from Resend |
| `SMTP_HOST` / `SMTP_USERNAME` / `SMTP_PASSWORD` | **leave empty** — you are using Resend |
| `LOCATIONIQ_API_KEY` | from LocationIQ |
| `SENTRY_DSN` | optional; leave empty to disable |

> **If you skip the R2 values the deploy still succeeds.** Nothing fails and
> nothing is obviously wrong: listings, search, accounts and the map all work.
> What does not work is pictures — every band photo and show poster upload
> answers `503 STORAGE_UNAVAILABLE`, and any image already stored serialises
> as `null`. The API prints a warning naming the unset variables at startup,
> so if uploads are failing, check the top of the API's deploy log before
> looking anywhere else.

You have to enter the R2 and mail values three times — once each for the API
and the two cron jobs. That is deliberate: the crons are separate processes and
Render does not share secrets between services.

`SECRET_KEY` and `JWT_SECRET` are generated by Render. Do not set them
yourself, and do not make them the same value — the app refuses to boot if they
match.

5. **Apply**. The first build takes 5–10 minutes.

> **On `R2_PUBLIC_BASE_URL`:** leaving it empty means every audio file and
> image is served through a short-lived signed URL. That is the safer default
> and what you want to start with. Set it only if you deliberately make the
> bucket public and want CDN caching.

## 2. Fix the API rewrite ⚠️

**This is the one step that will silently break things if you skip it.**

Render cannot interpolate a service URL into a route destination, so
`render.yaml` writes it out by hand. If the name `live-msc-api` was already
taken globally, Render appended a suffix and your real URL is different.

1. Open the **live-msc-api** service. Copy the URL at the top of the page.
2. If it is not exactly `https://live-msc-api.onrender.com`, edit
   [`render.yaml`](../render.yaml) — the `routes:` block under `live-msc-web` —
   to match, then commit and push.

Get this wrong and the site loads perfectly while every API call 404s, which is
a confusing way to spend an afternoon.

---

## 3. Point R2's CORS at the real origin

Now that you know the web URL, go back to the bucket's CORS policy and set
`AllowedOrigins` to it. Uploads will not work until you do.

### Backfill the bundled event posters

The API deploy deliberately does not run media backfills: a bad storage token
must not prevent an otherwise healthy API from starting. After confirming that
`R2_BUCKET` is the bucket scoped to the token and the token permission is
**Object Read & Write**, open the API service's Render Shell and run:

```bash
python scripts/seed_real_nyc.py --require-posters
```

Success ends with `posters missing: 0`. `AccessDenied` means the bucket name
and token scope do not match, or the token lacks write permission. Correct the
R2 values in the Render environment before retrying.

Until the backfill lands, nothing prints blank: a listing with no uploaded
poster falls back to a bundled house stock photograph matched to its genre
(`apps/web/public/stock/`, mirrored in the mobile bundle), and the same
fallback catches a poster URL that has expired on a long-open page. Real
posters always win over the stock the moment they exist.

---

## 4. Check it came up

```bash
curl https://live-msc-api.onrender.com/health
```

Expect `{"status":"ok"}`.

Then open the web URL. You should see the masthead and an empty bill — no
listings yet, which is correct.

Create an account through the UI. If the confirmation email arrives, mail is
working. If the address field suggests real addresses when you post a show,
LocationIQ is working. If a poster uploads, R2 and its CORS rule are working.

### If the API will not start

Read the logs. The app deliberately refuses to boot on a bad configuration
rather than serving traffic with it, and the message says exactly what is
wrong:

| Message | Cause |
|---|---|
| `JWT_SECRET must be at least 32 characters` | you set it by hand; let Render generate it |
| `JWT_SECRET must differ from SECRET_KEY` | you used one value for both |
| `DATABASE_URL must point at Postgres` | the database is not linked |
| `RATELIMIT_STORAGE_URI must be a shared store` | the key-value service is not linked |
| `TESTING is set outside a development environment` | remove that variable |

---

## 5. Attach your domain

1. **live-msc-web** → **Settings** → **Custom Domains** → add `livemsc.org`.
2. Add the CNAME record Render gives you at your DNS provider.
3. Update **`FRONTEND_URL`** on `live-msc-api` *and* on `live-msc-reminders` to
   `https://livemsc.org`.
4. Add the new origin to the R2 CORS policy.

Step 3 matters more than it looks: `FRONTEND_URL` drives CORS, the CSP, the
HTTPS redirect, and **every link in every email**. Leave it pointing at the
`.onrender.com` URL and your password-reset links will too.

## What runs on a schedule

Both are created by the Blueprint; you do not need to do anything.

| Job | When | What it does |
|---|---|---|
| `live-msc-reminders` | 15:00 UTC daily | emails tomorrow's shows to people going |
| `live-msc-sweeper` | 04:30 UTC daily | deletes R2 objects from uploads that were never finished |

The sweeper is not optional housekeeping — without it, abandoned uploads
accumulate silently and are billed every month.

You can run either by hand from the service page (**Trigger Run**) to check it
works.

## Deploying changes

Push to `main`. Render rebuilds automatically (`autoDeployTrigger: commit`).

Database migrations run in `preDeployCommand` **before** the new instance takes
traffic, so a deploy can never serve code against a schema it does not have. If
a migration fails, the deploy stops and the old instance keeps serving.

When you add a model change locally:

```bash
cd apps/server && .venv/bin/python -m flask --app app db migrate -m "what changed"
```

Read the generated file before committing it. Two things Alembic gets wrong on
its own, both of which will fail on a populated production table:

- A `NOT NULL` column needs a `server_default` to backfill existing rows.
- Never edit a migration that has already been applied. Add a new revision.

## Costs

| Resource | Plan | Monthly |
|---|---|---|
| `live-msc-api` | Starter | $7 |
| `live-msc-db` | Basic 256 MB | $6 |
| `live-msc-cache` | Free | $0 |
| `live-msc-web` | Static | $0 |
| Two cron jobs | Starter | ~$1 each, billed per run |

Roughly **$15/month**, plus whatever R2, Resend and LocationIQ cost above their
free tiers — which for a single city's listings is nothing.

The API cannot go on Render's free tier: free web services sleep after
inactivity, and a cold start on a listings page people open on their way to a
show is the wrong trade.

## One thing to know about scale

Two spend caps — `EMAIL_PER_RECIPIENT_HOURLY` and `LOCATIONIQ_DAILY_BUDGET` —
are counted **per process**, not shared across workers. The API runs 2 gunicorn
workers, so each effective ceiling is double what you set. Divide by the worker
count, or accept the doubling.

Making them exact means moving the counters into the key-value store the rate
limiter already uses. Worth doing if either ceiling starts mattering; not worth
the complexity before then.
